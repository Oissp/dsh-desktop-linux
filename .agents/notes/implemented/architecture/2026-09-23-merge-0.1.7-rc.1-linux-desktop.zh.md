# Agent Note: 0.1.7-rc.1 合并的 Linux 桌面开发目标

Status: implemented

[English](2026-09-23-merge-0.1.7-rc.1-linux-desktop.md) | 中文

## Problem

上游 0.1.7-rc.1 把构建目标变成未打包开发启动的显式输入：`development-project.ts` 把该输入标注为 `desktop-auto-update-environment.mjs` 的 `DesktopAutoUpdateTarget`，`desktop-build-paths.mjs` 新增 `desktopTargetPlatform` 与 `developmentRuntimeDirectory`，`dev.ts` 把 `resolveDesktopBuildTarget()` 传入其中。本 fork 只携带一个目标 `linux-x64`，并把 mac/win 目标词汇列入 [sync-trimmed-paths.txt](../../../../.github/sync-trimmed-paths.txt)。因此自动合并产出的树无法编译，也过不了自身 spec：类型导入指向被裁剪的文件，`desktopTargetPlatform` 仍在映射 `mac-*`/`win-x64` 名称，而 `SUPPORTED_TARGETS` 只接受 `linux-x64`，合并后的 `desktop-build-paths.spec.ts` 又断言 mac/win 映射与 mac/win 开发运行时目录。

同一次合并也无法自动解决 `apps/desktop/README.i18n.yaml`。其合并驱动用 `gitMergeInputPaths` 校验合并后的 owner 文件，而该函数取索引与 `GITHEAD_*` 合并头的树之并集。由于上游仍携带 `apps/desktop/tests/README.zh.md`，并集包含它，驱动便要求中文 README 链接 `.zh.md` 对应文件——正是 fork 有意替换为原始路径的上游写法（[fork 裁剪链接只做声明，不改写](../process/2026-09-20-fork-trimmed-link-gate.zh.md)）。常态门禁只读索引路径，因此接受 fork 写法；只有合并才会看到被裁剪的文件。

## Decision

**fork 的开发目标映射到 linux 载荷。** `desktopTargetPlatform` 接收 `DesktopBuildTargetName` 并返回 `{ platform: 'linux', arch: 'x64' }`；`assertSupportedTarget` 仍拒绝其他所有名称，因此 mac/win 目标会显式失败，而不是静默产出 linux 描述符。`DevelopmentProjectOptions.target` 为 `DesktopBuildTargetName`，被裁剪模块的导入已删除。`desktop-build-paths.spec.ts` 断言 linux 映射与 `targets/linux-x64/runtime/primary-runtime` 目录；`development-project.spec.ts` 与 `welcome-flow.e2e.ts` 传入 `linux-x64` 并断言 linux/x64 描述符。`developmentRuntimeDirectory` 及其 Windows 架构理由按上游原样保留——fork 解析的是同一个目标。

**配对记录手工重新登记。** `apps/desktop/README.md` 与上游逐字节相同；`apps/desktop/README.zh.md` 只在两处被裁剪的链接目标上不同。记录携带这两个 blob 哈希，由 `pnpm run verify-translation-pairing --write apps/desktop/README.md` 生成。

**桌面版本跟随引擎。** `apps/desktop/package.json` 为 `0.1.7-rc.1`，与合并后的根版本相同。fork 的 `.N` 构建计数仍可用于同一引擎版本的纯壳重打包。

## Alternatives considered

**保留上游的 mac/win 映射，只是挂在 fork 的守卫之后。** 否决：`assertSupportedTarget` 会拒绝该映射处理的每个目标，函数因此成为不可达代码，而其唯一调用方（`development-project.ts`）传入的是 `linux-x64`。

**删除 `desktopTargetPlatform`，把 `{ platform: 'linux', arch: 'x64' }` 内联。** 否决：这进一步偏离上游，上游下次重构描述符构造时又会冲突，并且丢掉了打包路径共用的目标名校验。

**在 `README.zh.md` 中采用上游的 `tests/README.zh.md` 链接写法。** 否决：这推翻了已记录的 fork 决定，`verify-md-links` 仍会把该目标当作已裁剪，而配对的两侧也会出现结构性分歧。

**让合并驱动从 `gitMergeInputPaths` 中减去裁剪路径。** 本次否决：这要改上游自有的脚本（`translation-pairing-merge.ts`），此后每次同步都得重新套用，而每次合并受影响的配对只有一个文件。手工重新登记是更小、可回退的代价。

## Consequences

fork 只保留一个桌面目标，因此上游今后改动 `desktop-build-paths.mjs`、`development-project.ts`、`dev.ts` 或桌面 README 配对时，都要重新套用 linux 映射与原始路径链接写法；本笔记点名这些文件，因为裁剪清单只记录被删除的文件，不记录被修改的行为。

上游对任何配对的修改，只要 fork 侧链接了被裁剪的目标，就会以无法解决的配对冲突落地，需要同样的手工重新登记。驱动在合并期更严格的视角，是 fork 得知上游存在被裁剪文件的唯一信号；它并不表示 fork 真的不一致，因此合并后 `pnpm run test:docs` 通过才是重新登记正确的确认。

`apps/desktop/tests/README.md` 及其 `.zh.md` 保持裁剪，因此桌面 README 指向它们的两处链接仍是声明式的，无法解析。

## Testing

`pnpm run typecheck` 编译合并后的树。`pnpm exec vitest run apps/desktop/tests`——`package-deb` 门禁——在 57 个文件中通过 570 个测试，含 `desktop-build-paths.spec.ts`、`development-project.spec.ts` 与 `welcome-flow.e2e.ts`。`pnpm run test:docs` 报告 20 passed、0 failed，覆盖配对语料与 markdown 链接；`pnpm run lint` 干净。
