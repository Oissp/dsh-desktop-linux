# Agent Note: 0.2.1-rc.1 merge — engine release and vendor 4.0.5 graduate, no fork conflict

Status: implemented

English | [中文](2026-10-17-merge-0.2.1-rc.1-linux-desktop.zh.md)

## Problem

Upstream `master` advanced four commits past the previous sync point (`dsh-v0.2.1-alpha.5`) and released engine `0.2.1-rc.1` (tag `dsh-v0.2.1-rc.1`, which is this merge's target). The delta touches 355 files, but every changed line is a `version` field: the engine release bumps `package.json` across the workspace to `0.2.1-rc.1`, and the accompanying vendor release graduates the nine vendored Cordis packages from `4.0.5-alpha.2`-style prerelease versions to their final `4.0.5`, `1.8.6`, `1.0.5`, `1.0.20`, `1.0.10`, `1.0.6`, `1.0.5`, `3.18.5`, and `1.1.7` values. No source file, test, snapshot, `pnpm-lock.yaml` entry, or documentation page changes.

The merge produced one conflict: `apps/desktop/package.json`, where the fork's metadata block meets the upstream version bump.

## Decision

**The single conflict keeps the fork's metadata and takes upstream's version.** `author` and `homepage` stay on the fork repository, and the version moves to `0.2.1-rc.1` (equal to the engine version). The conflict recurs on every sync for the same reason recorded in the alpha.3 and alpha.4 notes: the fork attaches its own publication and repository metadata to the same manifest the engine release bumps.

**No trim-list change.** The delta introduces no file, so nothing can arrive inside the trimmed macOS/Windows or publication scope. The list stays at 362 paths.

**No fork source change.** No upstream commit in this delta touches a forked Desktop file other than `apps/desktop/package.json`, and its only upstream change there is the version.

**No Agent Note sections beyond this record change.** The vendor `4.0.5` graduation is a version-only release: the vendored sources are byte-identical to the previous sync, so the fork's vendoring state is unchanged and no re-application of local modifications is needed.

## Alternatives considered

**Treat the version bump as a desktop-only release and skip the engine merge.** Rejected: the fork's desktop version tracks the engine version, and skipping the merge would leave `main` one release behind upstream while the desktop version claims a newer engine. The merge is also conflict-free apart from the manifest, so deferring it accumulates divergence for no benefit.

**Bump the desktop version to a `.N` suffix such as `0.2.1-rc.1.1`.** Rejected: the runbook assigns a `.N` suffix only when shell code changes. This sync changes no shell code, so the desktop version equals the engine version.

## Consequences

The next sync starts from upstream tag `dsh-v0.2.1-rc.1`. The trim list holds 362 paths.

Because `0.2.1-rc.1` is a release candidate rather than an alpha, the fork's release tag becomes `v0.2.1-rc.1` and `package-deb.yml` publishes it as a prerelease, matching the previous syncs' channel behavior. The updater continues to derive its channel from the version's prerelease segment rather than from `updater.channel`, so no `update-coordinator.ts` change is needed.
