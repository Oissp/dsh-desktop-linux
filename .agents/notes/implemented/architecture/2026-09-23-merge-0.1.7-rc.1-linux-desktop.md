# Agent Note: 0.1.7-rc.1 merge — the Linux desktop development target

Status: implemented

English | [中文](2026-09-23-merge-0.1.7-rc.1-linux-desktop.zh.md)

## Problem

Upstream 0.1.7-rc.1 made the build target an explicit input of the unpackaged development launch: `development-project.ts` types that input as `DesktopAutoUpdateTarget` from `desktop-auto-update-environment.mjs`, `desktop-build-paths.mjs` gained `desktopTargetPlatform` and `developmentRuntimeDirectory`, and `dev.ts` feeds `resolveDesktopBuildTarget()` into it. The fork carries one target, `linux-x64`, and lists the mac/win target vocabulary in [sync-trimmed-paths.txt](../../../../.github/sync-trimmed-paths.txt). Auto-merge therefore produced a tree that could not compile or pass its own specs: the type import named a trimmed file, `desktopTargetPlatform` still mapped `mac-*`/`win-x64` names while `SUPPORTED_TARGETS` accepts only `linux-x64`, and the merged `desktop-build-paths.spec.ts` asserted the mac/win mapping and the mac/win development runtime directories.

The same merge could not auto-resolve `apps/desktop/README.i18n.yaml`. Its merge driver validates the merged owner files with `gitMergeInputPaths`, which unions the index with the trees of the `GITHEAD_*` merge heads. That union contains `apps/desktop/tests/README.zh.md` because upstream still carries it, so the driver required the zh README to link its `.zh.md` counterpart — the upstream form the fork deliberately replaced with the authored path ([fork-trimmed links are declared, not rewritten](../process/2026-09-20-fork-trimmed-link-gate.md)). The steady-state gate reads index paths only, so it accepts the fork form; only a merge sees the trimmed file.

## Decision

**The fork's development target maps to a linux payload.** `desktopTargetPlatform` takes `DesktopBuildTargetName` and returns `{ platform: 'linux', arch: 'x64' }`; `assertSupportedTarget` still rejects every other name, so a mac/win target fails loud rather than silently producing a linux descriptor. `DevelopmentProjectOptions.target` is `DesktopBuildTargetName`, and the trimmed-module import is gone. `desktop-build-paths.spec.ts` asserts the linux mapping and the `targets/linux-x64/runtime/primary-runtime` directory; `development-project.spec.ts` and `welcome-flow.e2e.ts` pass `linux-x64` and assert the linux/x64 descriptor. `developmentRuntimeDirectory` and its Windows-architecture rationale are kept as upstream wrote them — the fork resolves the same single target.

**The pairing record is re-recorded by hand.** `apps/desktop/README.md` is byte-identical to upstream; `apps/desktop/README.zh.md` differs only in the two trimmed link targets. The record carries those two blob hashes, produced by `pnpm run verify-translation-pairing --write apps/desktop/README.md`.

**Desktop version follows the engine.** `apps/desktop/package.json` is `0.1.7-rc.1`, equal to the merged root version. The fork's `.N` build counter stays available for a shell-only repackaging of the same engine version.

## Alternatives considered

**Keep upstream's mac/win mapping behind the fork's guard.** Rejected: `assertSupportedTarget` would reject every target the mapping handles, so the function would be unreachable code whose only caller (`development-project.ts`) passes `linux-x64`.

**Delete `desktopTargetPlatform` and write `{ platform: 'linux', arch: 'x64' }` inline.** Rejected: it diverges further from upstream, so the next upstream refactor of the descriptor construction conflicts again, and it drops the target-name validation the packaging path shares.

**Adopt upstream's `tests/README.zh.md` link form in `README.zh.md`.** Rejected: it reverses a recorded fork decision, and `verify-md-links` then reports the target as trimmed anyway while the pair's two sides diverge structurally.

**Teach the merge driver to subtract trimmed paths from `gitMergeInputPaths`.** Rejected for this change: it edits an upstream-owned script (`translation-pairing-merge.ts`), which every future sync would then have to re-apply, and the affected pair is one file per merge. The manual re-record is the smaller, reversible cost.

## Consequences

The fork keeps one desktop target, so a future upstream change to `desktop-build-paths.mjs`, `development-project.ts`, `dev.ts`, or the desktop README pair re-applies the linux mapping and the authored-path link form; the note names those files because the trim list tracks only deleted files, not modified behavior.

Any upstream edit to a paired document whose fork side links a trimmed target lands as an unresolvable pairing conflict and needs the same manual re-record. The driver's stricter merge-time view is the fork's only signal that a trimmed file exists upstream; it does not indicate a real fork inconsistency, so `pnpm run test:docs` passing after the merge is the confirmation that the re-record is right.

`apps/desktop/tests/README.md` and its `.zh.md` stay trimmed, so the Desktop README's two links into them remain declared rather than resolvable.

## Testing

`pnpm run typecheck` compiles the merged tree. `pnpm exec vitest run apps/desktop/tests` — the `package-deb` gate — passes 570 tests across 57 files, including `desktop-build-paths.spec.ts`, `development-project.spec.ts`, and `welcome-flow.e2e.ts`. `pnpm run test:docs` reports 20 passed, 0 failed, covering the pairing corpus and markdown links; `pnpm run lint` is clean.
