# Agent Note: 0.2.1-rc.1 合并——引擎发版与 vendor 4.0.5 转正，无 fork 冲突

Status: implemented

[English](2026-10-17-merge-0.2.1-rc.1-linux-desktop.md) | 中文

## Problem

上游 `master` 在上一次同步点（`dsh-v0.2.1-alpha.5`）之后前进四个提交，发布引擎 `0.2.1-rc.1`（tag `dsh-v0.2.1-rc.1`，即本次合并的目标）。增量触及 355 个文件，但每一行改动都是 `version` 字段：引擎发版把工作区的 `package.json` 升到 `0.2.1-rc.1`，随附的 vendor 发版把九个 vendored Cordis 包从 `4.0.5-alpha.2` 这类预发布版本转为正式版 `4.0.5`、`1.8.6`、`1.0.5`、`1.0.20`、`1.0.10`、`1.0.6`、`1.0.5`、`3.18.5` 与 `1.1.7`。没有任何源码、测试、快照、`pnpm-lock.yaml` 条目或文档页面改动。

合并产生一处冲突：`apps/desktop/package.json`，即 fork 的元数据块与上游版本号 bump 相遇处。

## Decision

**唯一冲突保留 fork 元数据并采用上游版本号。** `author` 与 `homepage` 继续指向 fork 仓库，版本号升至 `0.2.1-rc.1`（与引擎版本相同）。该冲突在每次同步时都会重现，原因与 alpha.3、alpha.4 笔记记录的相同：fork 把自身的发布与仓库元数据挂在引擎发版要 bump 的同一个 manifest 上。

**裁剪清单不变。** 本次增量不引入任何文件，因此不可能有文件落入被裁剪的 macOS/Windows 或发布范围。清单保持 362 条。

**fork 源码不变。** 本增量没有任何上游提交改动 fork 修改过的 Desktop 文件（`apps/desktop/package.json` 除外），且该文件唯一的上游改动就是版本号。

**除本记录外无需改动其他 Agent Note。** vendor `4.0.5` 转正是纯版本发布：vendored 源码与上次同步逐字节相同，因此 fork 的 vendoring 状态未变，也不需要重新应用本地修改。

## Alternatives considered

**把版本 bump 当作桌面端单独发版而跳过引擎合并。** 拒绝：fork 的桌面版本跟随引擎版本，跳过合并会让 `main` 落后上游一个发布，而桌面版本却声称更新的引擎。本次合并除 manifest 外无冲突，推迟只会毫无收益地累积分叉。

**把桌面版本 bump 成 `0.2.1-rc.1.1` 这类 `.N` 后缀。** 拒绝：运行手册只在壳代码有改动时才加 `.N` 后缀。本次同步没有壳代码改动，因此桌面版本等于引擎版本。

## Consequences

下一次同步从上游 tag `dsh-v0.2.1-rc.1` 开始。裁剪清单保有 362 条路径。

由于 `0.2.1-rc.1` 是 release candidate 而非 alpha，fork 的发布 tag 变为 `v0.2.1-rc.1`，`package-deb.yml` 按预发布发布，与此前几次同步的频道行为一致。更新器仍从版本的预发布段推导频道，而不使用 `updater.channel`，因此 `update-coordinator.ts` 无需改动。
