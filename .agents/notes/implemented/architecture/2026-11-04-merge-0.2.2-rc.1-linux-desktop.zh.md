# Agent Note: 0.2.2-rc.1 上游同步 —— fork 保留单一更新源与 Linux 壳

Status: implemented

[English](2026-11-04-merge-0.2.2-rc.1-linux-desktop.md) | 中文

## Problem

上游 `master` 相对上一个同步点推进了 260 个提交，并发布了 `0.2.2-rc.1`。增量改动 1593 个文件——新增 133、删除 8、修改 1451、重命名 1——围绕网站安装器、CI 产物归档与保留、EdgeOne 清理恢复重建了 Desktop 发布管线。它还新增桌面渠道版本策略与分阶段灰度比例、会话菜单的 Open in app、subagent 目录命名、失败后继续生成、apply-patch 行摘要、CSS 锚定面板、CUA 应用审批界面、CUA 发布产物复用，以及 PTC 超时与调用上限处理。fork 在引擎侧的分叉仍是 tsdown 构建配置与一处 skill-office 版本断言；这些文件都没有冲突。

本次合并产生 71 个冲突：60 个落在裁剪清单内的 modify/delete 冲突（59 个清单文件，加上位于已裁剪目录下的 `apps/desktop/tests/updates/electron-updater/qualification.mjs`），以及 11 个内容冲突（`apps/desktop/package.json`、`apps/desktop/src/main.ts`、`apps/desktop/tests/update-coordinator.spec.ts`、桌面 README 双语对、CUA 原生 README 双语对，以及 `2026-08-25-electron-desktop-packaging-and-updates` 笔记三件套）。

## Decision

**合并采纳上游的渠道选择界面与 macOS 菜单改动，同时保留 fork 的单一更新源、Linux 托盘与裁剪后的发布管线。**

`apps/desktop/src/update-coordinator.ts` 保留 `configureUpdateFeed`：同一个 `latest-linux.yml` 服务所有发布，设置里的两个渠道都接受预发布，且 `updater.channel` 保持不设置，让 GitHub provider 解析 fork 的 `v<桌面版本>` tag。`update-coordinator.spec.ts` 保留单一更新源断言，并补充上游的过旧、相同与格式错误版本拒绝用例，但不断言渠道。

`apps/desktop/src/main.ts` 保留 fork 的外观控制器、语言控制器、打包 Linux 的 `Menu.setApplicationMenu(null)`、托盘与 desktop-cli 入口，并采纳上游的 macOS 编辑菜单（Shift+Command+V 粘贴并匹配样式，以及替换与语音子菜单）、`DesktopMessages` 类型导入与新增的语言文案。

`apps/desktop/package.json` 保留 fork 的产品名、作者、主页与 Linux 专用脚本，版本号取上游的 `0.2.2-rc.1`。

桌面 README 双语对采纳上游的渠道策略表述——发布者独立于版本后缀选择版本、正式版渠道也可以提供 alpha 或 RC 版本、省略 channel 时使用打包注入的默认值——同时保留 fork 的单一更新源事实：preload 将渠道选择标记为不可用，设置中不显示选择器，存储的值只在下次启动生效。

`2026-08-25` 打包笔记保留 fork 的 `package-deb.yml` 发布段落，描述从 `app-update.yml` 创建 GitHub Release 且不经 COS 上传。CUA 原生中文 README 采纳上游的工作流与源码复用文字，并保留 fork 指向已裁剪打包指南的英文目标链接，使双语对解析到同一目标。

**再裁剪九条上游路径，裁剪清单从 419 增至 428。** 上游新增的网站安装器、CI 归档与清理恢复脚本（`desktop-website-installer.ts`、`publish-website-ci.ts`、`archive-desktop-ci.ts`、`desktop-purge-recovery.ts`）导入已裁剪的发布模块，无法通过类型检查。它们的 spec 与 `desktop-channel-version.spec.ts` 是那些已裁剪模块的唯一读取者，而 `scripts/cua-helper/build-inputs.spec.ts` 导入已裁剪的 `desktop-package-environment.mjs`。fork 不运行这些流程。

**桌面版本等于引擎版本 `0.2.2-rc.1`，无需构建计数提升。** fork 的发布仓库还没有 `v0.2.2-rc.1`，合并落到 `main` 后打包 workflow 会发布该版本；版本一致也让 `check-workspace-constraints` 保持通过。

## Alternatives considered

**保留上游的 `selectUpdateChannel`。** 拒绝：fork 只发布一个更新源，且发布的版本全是预发布；钉住 `updater.channel` 会破坏 GitHub provider 的 tag 解析，而不是切换到另一个更新源。

**保留新的发布脚本并为其已裁剪导入提供占位。** 拒绝：它们服务于 fork 不运行的 macOS、Windows、COS 与 EdgeOne 流程；恢复它们会把已裁剪的发布管线重新带回代码树。

**用上游的渠道钉住测试替换 fork 的单一更新源测试。** 拒绝：fork 从不设置 `updater.channel`，上游断言按设计就会失败。版本排序用例本身有价值，已单独保留。

**让 CUA 中文 README 指向中文打包指南。** 拒绝：整个打包目录都被裁剪，且配对门禁要求两种语言解析到同一目标；英文目标与英文页一致。

**把桌面版本提升到 `.N` 计数。** 拒绝：`0.2.2-rc.1` 尚无发布，且同步合并保持桌面版本等于引擎版本。

## Consequences

下一次同步从 tag `dsh-v0.2.2-rc.1` 之后的上游 `master` 开始。合并推送到 `main` 后，打包 workflow 会发布 `v0.2.2-rc.1` 到 fork 的发布仓库，无需版本 bump。

裁剪清单记录 428 条路径。两项验证失败是继承而非本次引入：`pnpm run hygiene` 只有 `rescope-vendor:check` 失败，因为上游文档仍带有改名前的名称 token；仓库级单元测试仍会读取已裁剪的 workflow。

`pnpm install --frozen-lockfile` 通过。`pnpm run typecheck` 通过五个门禁。`pnpm run build:artifacts` 通过八个门禁，`pnpm run build:check` 通过两个。`pnpm run lint` 零错误、一个继承警告。`pnpm run test:docs` 通过全部 21 个门禁。`pnpm exec vitest run apps/desktop/tests` 通过 91 个文件、1161 个用例，跳过 5 个。`pnpm run hygiene` 通过 23 个门禁中的 22 个；`rescope-vendor:check` 按上述原因失败。
